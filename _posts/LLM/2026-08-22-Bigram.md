## 1. The Bigram Language Model

A language model assigns a probability to a sequence of characters. Written exactly, using the chain rule of probability, that's

$$
P(x_1,\ldots,x_T)=\prod_{t=1}^{T}P(x_t\mid x_1,\ldots,x_{t-1})
$$

— the probability of the whole sequence is the probability of the first character, times the probability of the second given the first, times the probability of the third given the first two, and so on. The problem is that the thing being conditioned on keeps growing with $t$, so this is impossible to estimate directly from a finite dataset.

A **bigram** model makes the simplest possible simplification, a first-order [Markov](https://en.wikipedia.org/wiki/Markov_chain) assumption: pretend the next character depends only on the one immediately before it, and throw away everything earlier.

$$
P(x_t\mid x_1,\ldots,x_{t-1})\approx P(x_t\mid x_{t-1})
$$

Every adjacent pair of characters becomes one training example. For `"emma"`:

```text
. → e,  e → m,  m → m,  m → a,  a → .
```

`.` is a single special token used for both the start and the end of a word, and it needs both roles simultaneously — as the *first* character of a pair it means "a word just started," as the *second* it means "the word just ended." Using one token for both works only because the two roles never collide: `.` never appears as both members of the same pair (that would mean an empty word). The alternative — separate `<START>` and `<END>` tokens — would double the special-token vocabulary for no real gain here, since the position in the pair already disambiguates the role. It would matter more in a model with a richer context window, where "have I just started" and "am I about to end" are genuinely different pieces of information the model might want to represent differently.

## 2. From Counting to Sampling

We count how often each ordered pair occurs across the whole dataset into a $27\times27$ table `N` (26 letters + `.`):

```python
N = torch.zeros((27, 27), dtype=torch.int32)
for w in words:
    chs = ['.'] + list(w) + ['.']
    for ch1, ch2 in zip(chs, chs[1:]):
        N[stoi[ch1], stoi[ch2]] += 1
```

$$
N_{ij}=\#\{t:x_{t-1}=i,\;x_t=j\}
$$

Visualized as a heatmap, darker cells are more frequent bigrams:

<img src="{{ '/assets/images/bigram/bigram_counts.svg' | relative_url }}" alt="bigram count heatmap" width="700">

Row `i` is "given that the current character is `i`, what came next" — so row `0` (the `.` row) specifically records what character *starts* a word, since `.` as the first member of a pair means "start." Running this on the actual 32,033-name dataset, `a` starts the most names by a wide margin (4,410 times), followed by `k` (2,963) and `m` (2,538).

### Counts aren't probabilities yet

Dividing each row by its own sum turns counts into something that looks like a probability distribution — each row sums to 1:

```python
P = N.float()
P = P / P.sum(1, keepdim=True)
```

It's worth being precise about what this is. This row is the **empirical (relative) frequency** with which each next-character actually followed `i` in the training data — a description of something that already happened, not yet a prediction about something that hasn't. We only get to *call* it a probability once we adopt it as our model's belief about what character comes next given `i`, and use it to make predictions on data it hasn't seen (technically, "density" refers to continuous variables; the discrete version of this table is usually just called an empirical distribution — but the underlying point stands regardless of the label: counting alone gives you a description, not a model, until you decide to *use* that description predictively.)

### Sampling

To generate a new name, start from the `.` context, sample the next character from that row's distribution, then repeat using the newly sampled character as the new context — until `.` is sampled again, which ends the word:

```python
g = torch.Generator().manual_seed(2147483647)
for _ in range(10):
    out = []
    ix = 0
    while True:
        p = P[ix]
        ix = torch.multinomial(p, num_samples=1, replacement=True, generator=g).item()
        out.append(itos[ix])
        if ix == 0:
            break
    print(''.join(out[:-1]))
```

Running this actually produces:

```text
cexze, momasurailezitynn, konimittain, llayn, ka, da,
staiyaubrtthrigotai, moliellavo, ke, teda
```

Not exactly names — bigram only ever looks one character back, so it has no way to know that `momasurailezitynn` is seventeen characters longer than any real name in the dataset. But it's clearly not noise either: it favors real digraphs (`th`, `ai`, `ll`) and plausible starts (`k`, `m`, `d`) because those are exactly what the counts told it to favor.

## 3. Measuring "Good": Negative Log-Likelihood

For the counting model, there's nothing left to evaluate — the row-normalized counts *are* the maximum-likelihood answer for this model class, which we can actually prove. For a fixed context $i$, we want $\hat\theta_{i,:}$ maximizing the log-likelihood of the observed data subject to $\sum_j \theta_{ij}=1$:

$$
\max_{\theta_{i,:}}\;\sum_j N_{ij}\log\theta_{ij}\quad\text{s.t.}\quad\sum_j\theta_{ij}=1
$$

Before reaching for the machinery, it's worth asking why a [Lagrange multiplier](https://en.wikipedia.org/wiki/Lagrange_multiplier) is even the right tool here. Without the constraint, this problem is trivial: $\log$ is increasing, so you'd just push every $\theta_{ij}\to\infty$. The constraint $\sum_j\theta_{ij}=1$ is what makes it a real problem — it means $\theta_{i,:}$ isn't free to move in every direction; it can only *redistribute* mass, since increasing $\theta_{ij}$ by some amount forces some other $\theta_{ik}$ to decrease by the same amount to keep the row summing to 1.

That reframes the question: at the optimum, is there any such redistribution left that would still help? Moving a sliver of mass from $\theta_{ik}$ to $\theta_{ij}$ changes the objective by (to first order) $N_{ij}/\theta_{ij}$ gained against $N_{ik}/\theta_{ik}$ given up. If those two marginal rates ever differed, the transfer would be a net win — meaning we weren't at the optimum yet. So at a genuine optimum, this marginal rate $N_{ij}/\theta_{ij}$ must be **the same constant across every $j$** — no permitted transfer left that helps. That shared constant is exactly what $\lambda$ turns out to be: the one number every outcome's marginal value has settled to at the optimum.

The Lagrangian is just a way of writing that equal-marginal-value condition as a single unconstrained problem instead of restating it in words for every pair $(j,k)$:

$$
\mathcal{L}=\sum_j N_{ij}\log\theta_{ij}-\lambda\Big(\sum_j\theta_{ij}-1\Big)
$$

Setting $\partial\mathcal{L}/\partial\theta_{ij}=0$ gives exactly $N_{ij}/\theta_{ij}=\lambda$ for every $j$ at once — the condition above, packaged into one equation per $j$ — which rearranges to $\theta_{ij}=N_{ij}/\lambda$. Substituting back into the constraint:

$$
\sum_j\frac{N_{ij}}{\lambda}=1\;\Longrightarrow\;\lambda=\sum_j N_{ij}=n_i\;\Longrightarrow\;\theta_{ij}=\frac{N_{ij}}{n_i}
$$

which is exactly the row-normalization we already did. (And since $\log$ is concave and a non-negatively-weighted sum of concave functions stays concave, this critical point is the unique global maximum over the simplex of valid probability rows — not just *a* good answer, but *the* best one this model class can produce.)

Once we move to a model with learnable parameters, though, we need a number to actually optimize — a loss. The natural one is the **negative log-likelihood** (NLL): for one example, $-\log P(x_t\mid x_{t-1})$, the probability the model assigned to what actually happened next, negated and logged.

$$
-\log(0.8)\approx0.22,\qquad-\log(0.01)\approx4.6
$$

Confidently correct costs almost nothing; confidently wrong costs a lot. As $P\to0$, $-\log P\to\infty$ — predicting near-zero probability for something that then actually happens is penalized without bound.

### Why this is also an entropy

Averaging NLL over the dataset is the same operation as estimating [cross-entropy](https://en.wikipedia.org/wiki/Cross-entropy) between two distributions: the true (empirical) distribution over next-characters, $p$, and the model's predicted distribution, $q$.

$$
H(p,q)=-\sum_j p_j\log q_j
$$

Cross-entropy decomposes cleanly:

$$
H(p,q)=H(p)+D_{KL}(p\,\|\,q)
$$

where $H(p)=-\sum_j p_j\log p_j$ is the entropy of the true distribution itself, and $D_{KL}(p\|q)=\sum_j p_j\log(p_j/q_j)$ — the [Kullback–Leibler divergence](https://en.wikipedia.org/wiki/Kullback%E2%80%93Leibler_divergence) — measures how far the model's guess $q$ is from the truth $p$. $D_{KL}\ge0$ always, with equality exactly when $q=p$. So $H(p,q)\ge H(p)$: no matter how good $q$ gets, cross-entropy can never drop below the true distribution's own entropy, because that entropy is the randomness genuinely present in the data, not a shortcoming of the model.

Running the count model's NLL over the entire 228,146-bigram dataset gives:

$$
\text{average NLL}\approx2.4544
$$

Because Section 3's derivation already showed the row-normalized counts are the *unique optimal* $\theta$ for any bigram-structured model, this number isn't just "how well counting happened to do" — it's the floor for the entire model class. It *is*, in effect, $H(p)$ for a data-generating process that only remembers one character of context: the irreducible uncertainty in "what letter comes next, given only the letter right before it." No bigram model, however it's trained, can beat 2.4544 on this data. Going lower requires conditioning on more context than a bigram structurally allows — which is exactly the motivation for the next lecture's MLP model.

## 4. The Same Model as a Neural Network

Now the interesting part: build the *identical* model, but with gradient descent instead of counting.

Each character becomes a one-hot vector, so the network sees "which character" without inventing a fake numeric ordering between characters:

```python
xenc = F.one_hot(xs, num_classes=27).float()
logits = xenc @ W          # W: (27, 27)
```

Because the input is one-hot, this matmul doesn't really "compute" anything in the usual sense — $e_i^\top W=W_{i,:}$, a row lookup dressed up as a matrix multiply. That's exactly why this network can represent the bigram model and nothing more: it has the same $27\times27=729$ free numbers the count table `N` had.

`logits` are unconstrained real numbers — not yet a probability. Getting there is three steps:

```python
counts = logits.exp()
probs = counts / counts.sum(1, keepdim=True)
```

`exp` specifically buys us three things simultaneously: it's always positive ($e^z>0$ for any $z$, so $\log$ of the resulting probability is always defined — no special-casing zero), it preserves ranking (increasing $z$ increases $e^z$, so the highest-scoring character stays highest-scoring), and it's shift-invariant — adding the same constant to every logit in a row leaves the resulting probabilities unchanged, because the added factor is common to numerator and denominator and cancels. This three-step sequence (raw score → exponentiate → normalize) is exactly [softmax](https://en.wikipedia.org/wiki/Softmax_function), and the name `counts` isn't accidental: since $p_j\propto e^{z_j}$, setting `logits` to $\log(\text{some count row})$ would exactly reproduce the count model — `logits` behave structurally as *log-counts*, and `counts = logits.exp()` is playing the same role $N$ played, just filled in with learned real numbers instead of observed integers.

The loss is the same NLL as before, now written as a function of `W`:

```python
loss = -probs[torch.arange(num), ys].log().mean()
```

Training this from scratch on the full dataset:

```text
step    0: loss 3.7686
step   20: loss 2.5823
step   40: loss 2.5213
step  100: loss 2.4900
step  199: loss 2.4830
```

— converging toward that same 2.4544 floor from Section 3, approached from the other direction: not by a closed-form formula, but by nudging 729 numbers downhill, step after step.

## 5. Same Machine, Different Target

Nothing here is a new training procedure. It's the exact loop from the [micrograd post](https://jungjinuuu.github.io/llm/2026/08/14/micrograd.html):

```text
forward → compute loss → backward → update parameters → zero gradients → repeat
```

```python
for k in range(num_steps):
    xenc = F.one_hot(xs, num_classes=27).float()
    logits = xenc @ W
    counts = logits.exp()
    probs = counts / counts.sum(1, keepdim=True)
    loss = -probs[torch.arange(num), ys].log().mean()

    W.grad = None
    loss.backward()
    W.data += -50 * W.grad
```

The only thing that changed between micrograd's toy regression and this is the **forward pass and the loss**: there, `output = tanh(...)` and `loss = sum((pred - target)**2)`; here, `output = softmax(one_hot(x) @ W)` and `loss = -log(prob of the actual next char)`. `loss.backward()` doesn't care which forward pass or which loss produced the computational graph — it just walks it backward. Whatever number you decide to minimize, and however you decide to compute it, plug it into the same four-step loop and gradient descent will push your parameters toward it.

## 6. Smoothing and Regularization Are the Same Idea, Twice

Two problems, solved on opposite sides of this same model, turn out to be the same fix.

**On the counting side:** any bigram that never appeared in training gets `N=0`, and $-\log(0)=\infty$ — one unseen pair anywhere in a test word makes the whole evaluation infinite. The fix is additive smoothing: add a small constant before normalizing.

```python
P = (N + 1).float()
P = P / P.sum(1, keepdim=True)
```

Every cell is now strictly positive, so no bigram is ever assigned exactly zero probability. As the added constant grows, every row gets pulled closer to uniform — the counts eventually get drowned out entirely, and in the limit every next-character becomes equally likely.

**On the neural-net side**, the equivalent problem is overfitting: without any constraint, `W` is free to grow arbitrarily large in whatever direction drives the training loss down, including memorizing quirks of this exact dataset. Karpathy's fix is [L2 regularization](https://en.wikipedia.org/wiki/Ridge_regression) — adding a penalty on the size of `W` directly into the loss:

```python
loss = -probs[torch.arange(num), ys].log().mean() + 0.01*(W**2).mean()
```

Training with this penalty added converges to a slightly *higher* loss than the unregularized version — around **2.483** instead of 2.4544 after 200 steps in my run — and that gap is the cost of the fix, not a bug: the penalty is actively pulling every entry of `W` toward 0. Since `counts = logits.exp() = exp(one_hot(x) @ W)`, pushing `W` toward 0 pushes every logit toward 0, which pushes every `count` toward $e^0=1$ — i.e., toward a **uniform** distribution across all 27 characters. That's the exact same limiting behavior additive smoothing produces on the count side, just reached by a different mechanism: smoothing adds a constant directly to the counts; regularization shrinks the parameters that get exponentiated into the counts. Same destination — pull everything toward uniform, in proportion to how little evidence supports deviating from it — different route.

*(One distinction worth knowing about but not covered in depth in this lecture: L2's penalty $\sum w^2$ shrinks every weight smoothly, generally without forcing any of them to exactly zero — this is why it's often called "weight decay." L1's penalty $\sum\lvert w\rvert$ has a kink at zero that L2 doesn't, and that kink is what actually drives some weights to land exactly on zero, effectively performing feature selection. Karpathy uses L2 here, so that's the version this post's numbers reflect.)*

## 7. Closing Thoughts

Main things I want to remember from this one:

- A bigram model is the chain rule of probability plus a first-order Markov assumption: predict the next character from only the one before it.
- Row-normalized counts aren't just a reasonable estimate — they're the exact, unique solution to constrained maximum-likelihood estimation, provable with a Lagrange multiplier.
- Averaged NLL is cross-entropy, which decomposes into the data's own entropy plus how far off the model is (KL divergence) — so there's a hard floor no bigram model can beat, and counting already reaches it.
- The neural-net version is the identical model — same 729 free parameters, same softmax, same NLL — just found by gradient descent instead of a closed-form formula, and it converges to that same floor.
- Nothing about the training loop itself changed from micrograd; only the forward pass and the loss did.
- Additive smoothing and L2 regularization are the same underlying fix — pull toward uniform in the absence of evidence — applied on two different sides of the same model.

The part I keep coming back to is Section 3: the row-normalization we do almost on reflex — "just divide by the total" — isn't an ad hoc trick. It's *forced* by maximizing likelihood under a probability constraint; the Lagrange multiplier turns out to equal the row sum, and that's the whole derivation. That's the pattern I want to keep chasing through this series: formulas that look like conventions usually aren't. They're what the constraints and the objective leave no other choice but to produce.

Same pursuit as last time: I want AI that feels as natural as the math underneath it, not a pile of conventions to memorize — Section 3 was one small proof that it can be.
