This is my third post in the *Zero to Hero* series, following [Building a bigram language model](https://jungjinuuu.github.io/llm/2026/08/22/Bigram.html). Bigram was one of the simplest language models there is, and it showed us its own ceiling pretty directly: with only one character of context, no amount of training can push the loss below about 2.45 on this dataset — that's not a bug, it's the entropy floor of a model that structurally can't remember more than one character back (see Section 3 of the [previous post](https://jungjinuuu.github.io/llm/2026/08/22/Bigram.html) for the proof). This time we keep the same goal — predict the next character — but reach for a strictly more expressive model: the MLP.

As before, I recommend implementing this yourself rather than just reading it. The lecture is [here](https://www.youtube.com/watch?v=TCH_1BHY58I), and the code lives in [karpathy/makemore](https://github.com/karpathy/makemore).

## 1. From Bigram to MLP: Bengio's Distributed Representations

Bigram's ceiling isn't really about bigram specifically — it's about *counting*. If we wanted more context, the naive fix is to count longer sequences: trigrams instead of bigrams, or 4-grams. But the table this requires grows as $V^n$ for context length $n$ and vocabulary size $V$. At the character level here, $V=27$, so 2 characters of context means $27^2=729$ rows, 3 characters means $27^3\approx19{,}683$, 4 characters means $27^4\approx531{,}441$ — and most of those rows would be counting bigrams, trigrams, or n-grams that never occur in a 32,033-name dataset. This is the **curse of dimensionality**: the space of possible contexts grows exponentially, while the data to fill it in grows only linearly (more names). Counting simply runs out of data before it runs out of table.

The lecture builds on Bengio et al.'s [*A Neural Probabilistic Language Model*](https://www.jmlr.org/papers/volume3/bengio03a/bengio03a.pdf), and its fix isn't to count longer sequences — it's to stop treating each character as a completely separate, unrelated symbol. Instead, learn a **distributed representation** (an embedding) for each character: a point in a low-dimensional continuous space, positioned so that characters playing similar roles end up near each other. A sequence that was never observed during training can still get a reasonable probability if the characters in it are represented similarly to characters in sequences that *were* observed — generalization by interpolation in embedding space, rather than needing every exact combination memorized.

The architecture:

```text
3 previous characters
        ↓
embedding lookup (each → a low-dim vector)
        ↓
concatenate
        ↓
hidden layer (tanh)
        ↓
output layer → logits over 27 characters
        ↓
softmax → probabilities
```

Two things get learned *simultaneously*: the embeddings themselves, and the function that turns a sequence of embeddings into a prediction. Neither is fixed in advance — the training signal (predicting the next character) shapes both at once.

## 2. Dataset & Context Window

Where bigram's training example was one character predicting the next, MLP fixes a **context length** and uses that many preceding characters:

```python
block_size = 3
X, Y = [], []
for w in words:
    context = [0] * block_size
    for ch in w + '.':
        ix = stoi[ch]
        X.append(context)
        Y.append(ix)
        context = context[1:] + [ix]
```

For `"emma"`, this slides a window of 3 across the word (padding the start with `.`, index 0):

```text
... → e
..e → m
.em → m
emm → a
mma → .
```

`context = context[1:] + [ix]` drops the oldest character and appends the one just seen, sliding the window forward by one position each step. The result: `X.shape == (N, 3)`, `Y.shape == (N,)` — same shape of problem as before (many `(context, target)` pairs), just with a context of 3 characters instead of 1.

## 3. Architecture and Training

### Embeddings

Each of the 27 characters gets a learned vector:

```python
C = torch.randn((27, n_embd))
emb = C[X]     # (N, 3) → (N, 3, n_embd)
```

`C[X]` looks up a row of `C` for every position in every context at once. It's worth being precise about what "lookup" means here: for a single index, `C[5]` is exactly what you'd get from `F.one_hot(torch.tensor(5), num_classes=27).float() @ C` — a one-hot vector times `C` just selects row 5. `C[X]` is that same operation, vectorized: it's the efficient, indexing form of what a one-hot matmul against `C` would compute, without ever constructing the wasteful all-zeros-but-one intermediate.

The three per-position embeddings then need to become one vector before the hidden layer:

```text
(N, 3, n_embd) → (N, 3·n_embd)
```

```python
h = torch.tanh(emb.view(-1, 3*n_embd) @ W1 + b1)
```

`.view()` reshapes `emb` for free — no data is copied. That's only possible because PyTorch tensors separate the actual data (`storage`) from the metadata describing how to read it (`size`, `stride`, `offset`); `emb` is already laid out contiguously in memory in exactly the order `.view(-1, 3*n_embd)` wants to read it, so reshaping is just a change of reading instructions, not a new tensor. (Concatenating the same three slices with `torch.cat` instead would *not* be free — `cat` always allocates a new buffer and copies into it, since it has no way of knowing the pieces already sit contiguously in the source tensor.)

`emb.view(-1, 3*n_embd) @ W1` has shape `(N, n_hidden)`, while `b1` has shape `(n_hidden,)` — PyTorch broadcasts `b1` as `(1, n_hidden)` and adds it to every row, so the same bias vector applies to every example in the batch (not a separate bias per example; each of the `n_hidden` *neurons* does have its own entry in `b1`, but that's an axis apart from the batch).

### From logits to a loss

```python
logits = h @ W2 + b2
loss = F.cross_entropy(logits, Y)
```

This is the same NLL objective as the bigram model's, just computed differently. Writing it out manually would look like:

```python
counts = logits.exp()
probs = counts / counts.sum(1, keepdim=True)
loss = -probs[torch.arange(N), Y].log().mean()
```

`F.cross_entropy` is preferred over this for two concrete reasons, not just brevity. **Numerical stability**: if any logit is large, `logits.exp()` can overflow to `inf` — but softmax is invariant to shifting every logit in a row by the same constant (the shift cancels between numerator and denominator), so subtracting `logits.max()` before exponentiating leaves the result unchanged while keeping every intermediate value finite. `F.cross_entropy` applies this shift internally. **Efficiency**: the manual version builds `counts` and `probs` as full intermediate tensors before indexing into them; `F.cross_entropy` fuses the softmax and the NLL into one computation and never materializes `probs` explicitly.

For `n_embd=2` and `n_hidden=100`, this network has **3,481** learnable parameters (`C`: 54, `W1`+`b1`: 700, `W2`+`b2`: 2,727) — orders of magnitude more than bigram's 729, but still tiny by modern standards, and small enough to train on a laptop in seconds.

## 4. Learning Rate

Training is gradient descent on this loss surface, same loop as always — `forward → loss → backward → update`. But there's an honest gap here compared to the [previous post](https://jungjinuuu.github.io/llm/2026/08/22/Bigram.html): for the counting model, we could *prove* the loss surface was concave, so there was a unique global optimum and no question of ever getting stuck. For this network, there's no such guarantee. `tanh` is nonlinear, and the composition of two matrix multiplies with a nonlinearity between them is not concave (or convex) in the parameters in any simple, provable way. Gradient descent doesn't know this in advance either — it just follows the local downhill direction, wherever that happens to point. Whether that leads to a genuinely good optimum, or gets stuck somewhere worse, isn't something the math guarantees up front for a network this shape; in practice, it tends to work out well enough for problems like this one, but the certainty we had for bigram is gone.

That makes the step size — the **learning rate** — a real hyperparameter to get right, not an afterthought. Near any point on the loss surface, the surface looks approximately like a bowl (a local quadratic approximation); too small a step and you crawl toward the bottom of that bowl at a glacial pace; too large a step and you overshoot past the bottom entirely, landing higher on the *opposite* wall of the bowl than where you started — which can bounce you back and forth (oscillation) or, if the overshoot compounds step after step, blow up entirely (divergence).

### Finding a good region

Rather than guess, the lecture searches: try a very small rate and a very large one to bracket a reasonable range, then sweep a grid of rates spaced *logarithmically* in between (since the right order of magnitude, not the right rate to two decimal places, is what actually matters at this stage):

```python
lre = torch.linspace(-3, 0, 1000)
lrs = 10**lre

lri, lossi = [], []
for i in range(1000):
    ix = torch.randint(0, Xtr.shape[0], (32,))
    emb = C[Xtr[ix]]
    h = torch.tanh(emb.view(-1, 3*n_embd) @ W1 + b1)
    logits = h @ W2 + b2
    loss = F.cross_entropy(logits, Ytr[ix])

    for p in parameters:
        p.grad = None
    loss.backward()
    lr = lrs[i]
    for p in parameters:
        p.data += -lr * p.grad

    lri.append(lre[i].item())
    lossi.append(loss.item())
```

The loss falls as the rate increases from $10^{-3}$, bottoms out somewhere around $10^{-1}$, then rises sharply as the rate approaches $1$ — that rise on the right is the overshoot/divergence regime from above, made visible. Running this actually puts the minimum around $\text{lr}\approx10^{-1}$, which is the region to train in.

### Why decay it later

This is one search, not a fixed setting for the whole run — a large learning rate that's efficient for closing the initial distance to a good region becomes a liability once you're already near a good spot: each large step risks bouncing back out of the good region it just found. The pattern the lecture uses is to train at a found-good rate first, then **decay** it (drop it, e.g. by 10x) partway through training. This has the same shape as the exploration/exploitation split that shows up in reinforcement learning: early on, larger steps let the parameters cover a lot of ground and find a broadly good region of the loss surface — akin to *exploration* — while later, smaller steps let those parameters settle and refine within that region without the risk of a large step kicking them back out — akin to *exploitation*. Concretely, in my run: 30,000 steps at $\text{lr}=0.1$ brought the loss down substantially; switching to $\text{lr}=0.01$ for another 30,000 steps squeezed out further, smaller gains without the loss bouncing around.

## 5. Train / Dev / Test

A low training loss on its own doesn't tell you the model is good — it might just mean the model has memorized the training set rather than learned anything that generalizes. To measure that honestly, the dataset gets split three ways:

```text
train (≈80%)  → fit the parameters
dev   (≈10%)  → compare model/hyperparameter choices
test  (≈10%)  → one final, unbiased performance check
```

The reason for three sets rather than two is that `dev` gets *reused* — every time you try a different hidden layer size, a different learning rate, a different context length, you're picking whichever choice does best on `dev`. That repeated reuse means your choice of hyperparameters is, in a small way, fit to `dev` too, the same way parameters get fit to `train`. `test` is only touched once, at the very end, specifically so there's a set your choices were never optimized against, giving an honest read of how the model performs on data it's never influenced in any way.

In the lecture's flow — and in the notebook this post is based on — the model is first trained on the *entire* undivided dataset, and the train/dev/test split is introduced only afterward, as a followup concern once overfitting comes up. In practice, you'd want `dev` in the loop *during* training, not just checked once at the end: evaluate on `dev` periodically as training proceeds, and if `train` keeps falling while `dev` starts climbing, that gap is the signal to stop early, before the model wanders further into memorizing the training set's specific quirks — rather than only discovering, after the fact, that it already had.

This is the classic **bias–variance tradeoff**: too little model capacity (or too little training) underfits — both `train` and `dev` loss stay high and close together, because the model hasn't learned enough of anything yet (high bias). Too much capacity relative to the data can overfit — `train` loss keeps dropping while `dev` loss turns and rises, because the model is starting to fit noise specific to the training set rather than the underlying pattern (high variance).

<img src="{{ '/assets/images/mlp/bias_variance.svg' | relative_url }}" alt="bias-variance tradeoff" width="600">

Running the actual splits on this dataset (182,625 / 22,655 / 22,866 examples for train/dev/test):

```text
train: 2.3256
dev:   2.3256
test:  2.3248
```

All three essentially match — which says this particular model (3,481 parameters) isn't anywhere near overfitting on this much data; if anything, there's room to make it bigger before generalization would start to suffer.

With `n_embd=2`, the learned character embeddings can be plotted directly, no dimensionality reduction needed (for higher embedding dimensions, this is normally done with something like t-SNE or PCA to project down to 2D first):

A few things fall out without being told to: the vowels (`a`, `e`, `i`, `o`, `u`) sit in a loose cluster distinct from the consonants, which is exactly the kind of structure Section 1 predicted — characters that play similar distributional roles end up near each other, purely as a side effect of the training objective, with no supervision telling the model "these are vowels." `.` sits off on its own, well away from every letter, which also makes sense: as both start-of-word and end-of-word, its role in context is genuinely unlike any letter's.

### Putting the numbers side by side

```text
bigram (1 char of context):  2.4544  (proven floor for this model class)
MLP    (3 chars of context): 2.3248  (test loss)
```

The MLP beats bigram's un-beatable floor, because it isn't the same model class — it isn't limited to one character of memory, and it isn't restricted to representing each character as a totally separate, unrelated symbol. Both of those relaxations (more context, distributed representations) came directly from the ideas in Section 1, and the gap between 2.4544 and 2.3248 is what actually cashing them in looks like.

## 7. Closing Thoughts

Main things I want to remember from this one:

- The curse of dimensionality is why counting doesn't scale with context length: the table size grows as $V^n$, and real data can't fill it in.
- Bengio's fix is to learn distributed representations — embeddings — so unseen combinations can still get reasonable probability if their pieces resemble pieces seen elsewhere.
- `C[X]` is the efficient, indexing form of a one-hot matmul; `.view()` is free because it only changes how existing memory is read, while `torch.cat` always copies.
- `F.cross_entropy` isn't just shorthand for manual softmax + NLL — it's numerically safer (shift-invariance avoids `exp()` overflow) and doesn't materialize an intermediate `probs` tensor.
- Unlike the bigram model, this loss surface isn't provably concave — gradient descent here is a local search with no guarantee of a unique global optimum, just a good empirical track record.
- A learning-rate range test finds a good order of magnitude to train at; decaying it partway through mirrors an exploration/exploitation split — big steps first to find a good region, small steps later to refine within it.
- Train/dev/test exists because `dev` gets reused across every modeling choice, so `test` has to stay untouched until the very end to give an honest number; the gap between `train` and `dev` loss is literally what bias and variance look like in numbers.
- More context and distributed representations together beat bigram's un-beatable floor — 2.3248 versus 2.4544 — because they're a genuinely different, less restricted model class.

What I keep sitting with from this one is Section 1: bigram wasn't a bad model because someone chose a bad loss or forgot a trick — it was *exactly as good as a model of its restricted class could be* (we proved that with the Lagrange multiplier argument last post). Getting past that ceiling required changing the *class* of model entirely, not tuning the one we had. That's a pattern I expect to see again and again in this series: real progress in this field often isn't found inside a model class by optimizing harder, it's found by relaxing an assumption the earlier class was quietly built on.

Next up: batch normalization, and a much closer look at what's actually happening inside training — the statistics of activations and gradients as they flow through the network, which is where a lot of the practical difficulty in training deeper networks turns out to live.
